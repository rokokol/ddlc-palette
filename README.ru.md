Единственный источник правды для всего, что я делаю в стиле DDLC, чтобы один и тот же розовый не подбирался на глаз в пятый раз. Источник — [`palette.json`](palette.json), всё в [`dist/`](dist) из него генерируется и коммитится, так что потребителю без Nix достаточно прочитать файл

## Откуда взяты числа

Не со скриншота и не на вкус — с самого [ddlc.moe](https://ddlc.moe/):

| | что прочитано |
| --- | --- |
| **интерфейс** | `main.css` — разделитель, кнопка и её hover, цвет ссылок, тёмный футер |
| **dot**, **paper** | `images/tilebg.png`, фоновый тайл сайта: 200×200, кружки радиуса 40 на решётке со сдвигом в полшага, `#FFDBF0` на белом |
| **персонажи** | спрайты `sticker_?.png`: самый частый цвет волос по верхней части головы, глаза Сайори и Моники, волосы Юри в тени |
| **форма** | те же четыре спрайта: пиджак и юбка в складку — единственный средний серый палитры и её тёмный синий |
| **блокнот** | `images/screen2.png`, мини-игра с поэмами: ленточка обложки и линовка — два тона, которых нет ни на одном спрайте: зелёный, достаточно тёмный для белого, и единственный синий, читаемый на любом фоне |
| **акценты** | `images/screen5.png`, два тона банта Сайори — другого сильного красного на сайте нет |

Придуманного здесь ничего нет. Где сайт рисует плоскую заливку, замер — её самый частый пиксель, и таковы все цвета выше, кроме одного. Ирис Моники — плавный переход: 64 оттенка на 68 пикселях, четыре из них делят первое место по два пикселя. Выбор между равно частыми оттенками — не замер, поэтому именно здесь правило разветвляется и `monikaEye` берётся как среднее по всему набору. О каждом таком ветвлении `canonize.sh` пишет в stderr, так что метод не может смениться незаметно

У каждой записи в `palette.json` есть свои `where`, `source` и `method`, так что происхождение любого цвета прослеживается, и ни один хекс не скрывает, как именно он получен:

| `method` | как получен хекс | сколько |
| --- | --- | --- |
| `declared` | взят прямо из объявления в `main.css` — мерить нечего | 6 |
| `mode` | самый частый пиксель из всего, что принял предикат цвета | 13 |
| `mean` | среднее по тому же набору, потому что первое место разделили поровну — сегодня это только `monikaEye` | 1 |

Три метода и никакого четвёртого: каждая запись — та, которую `canonize.sh` перечитывает, а проверка не пропускает запись без любого из четырёх полей или с `method` вне этого списка, так что цвет, добавленный позже, не сможет прийти без происхождения

## Как пользоваться

**Nix.** Флейк отдаёт палитру просто данными — ни модуля, ни опций, включать нечего:

```nix
{
  inputs.ddlc-palette.url = "github:rokokol/ddlc-palette";

  # inputs.ddlc-palette.lib.palette.plum       ->  "#BB5599"
  # inputs.ddlc-palette.lib.bare.plum          ->  "BB5599"   (hyprland, hyprlock, mako)
  # inputs.ddlc-palette.lib.rgba.plum "0.55"   ->  "rgba(187, 85, 153, 0.55)"   (GTK-CSS, rofi)
  # inputs.ddlc-palette.lib.annotated          ->  по группам, с происхождением
  # inputs.ddlc-palette.lib.base16.dark.base0D ->  "#6868B4"
}
```

**Всё остальное.** Бери файл, который подходит:

| файл | вид |
| --- | --- |
| `dist/palette.css` | `:root { --ddlc-plum: #BB5599; … }` |
| `dist/palette.nix` | `{ plum = "#BB5599"; … }` |
| `dist/palette.sh` | `DDLC_PLUM='#BB5599'` — сорсится |
| `dist/palette.env` | `plum=BB5599` — голый хекс, для конфигов, которые не терпят `#` |
| `dist/palette.svg` | карточка со свотчами сверху |
| `dist/base16-ddlc-dark.yaml` | схема base16, рядом лежит `-light.yaml` |

## Как тема

`dist/base16-ddlc-{light,dark}.yaml` — схемы [base16](https://github.com/tinted-theming/home), так что сотни уже существующих шаблонов сами сделают из них конфиг для терминала, редактора или шелла; ничего привязанного к конкретному приложению здесь не лежит:

```sh
base16-builder --scheme dist/base16-ddlc-dark.yaml --template kitty
```

Каждый слот называет ключ палитры, из которого взят, как этот ключ получен и откуда, так что схема читается сама по себе:

```yaml
base02: "#4B669E" # skirt (mode) — the sticker_?.png sprites, the pleated skirt
```

| слот | | dark | light |
| --- | --- | --- | --- |
| `base00` | фон | `ink` | `paper` |
| `base01` | фон посветлее | `yuri` | `dot` |
| `base02` | выделение | `skirt` | `natsuki` |
| `base03` | комментарии | `jacket` | `jacket` |
| `base04` | тусклый текст | `natsuki` | `yuri` |
| `base05` | **текст** | `blush` | `yuriShadow` |
| `base06` | яркий текст | `dot` | `ink` |
| `base07` | светлый фон | `paper` | `blush` |
| `base08` | красный | `bow` | `bow` |
| `base09` | оранжевый | `sayori` | `sayori` |
| `base0A` | жёлтый | `monika` | `monika` |
| `base0B` | зелёный | `monikaEye` | `ribbon` |
| `base0C` | голубой | `sayoriEye` | `rule` |
| `base0D` | синий | `rule` | `skirt` |
| `base0E` | пурпурный | `pink` | `plum` |
| `base0F` | коричневый | `bowShadow` | `bowShadow` |

Акценты у вариантов разные, потому что палитра полярная: цвет, читаемый на `ink`, на `paper` — пастель. `base00`–`base06` упорядочены по светлоте, а каждый остальной слот берёт 3:1 к своему фону — кроме трёх мест, которые диктует материал:

- **жёлтого и оранжевого на сайте нет вообще.** `base09` и `base0A` несут два тёплых цвета персонажей, и в светлом варианте это скорее оттенки, чем акценты (1.96:1 и 2.77:1)
- **красный ровно один**, бант Сайори, поэтому `base08` в тёмном варианте — 2.77:1
- `base0F` сам base16 называет редко используемым, там лежит более тёмный из этих двух красных

`ash` — единственная запись палитры, которую не берёт ни один слот: нейтральный серый, по светлоте зажатый между двумя розовыми, он разорвал бы ту самую рампу, в которую иначе встал бы. Остальное держит проверка: шестнадцать заполненных слотов на вариант, ни одного цвета дважды и рампа, которая не поворачивает назад

## Перечитать сайт

Происхождение выше — просто утверждение, пока его что-нибудь не воспроизводит, поэтому есть `canonize.sh`: качает `main.css`, тайл, четыре спрайта и два скриншота, заново замеряет все цвета и пишет `palette.json` и `dist/` — рядом с каждым хексом его `method`. На сегодняшнем сайте он воспроизводит каждый хекс из этого репозитория точь-в-точь

```sh
nix develop -c ./canonize.sh   # или curl, jq, imagemagick, awk в PATH
```

Каждый цвет — одна строка, называющая не «где вырезать», а «как он выглядит»: `pick` принимает awk-предикат по `hex`, `r`, `g`, `b`, `sat`, `lum`, `x` и `y` и возвращает самый частый подходящий пиксель. Так область опознаётся по своему цвету, а не по координатам, которые сломает редизайн:

```sh
jacket=$(sprites | pick 'sat < 0.25 && lum > 120 && lum < 200 && r > b')
```

Тонкая мода — не слабая: 27 повторов на 1721 пикселе из 1446 оттенков значит, что повторы и *есть* плоская внутренность, а всё остальное — сглаженная кромка. Поэтому мода выигрывает всюду, где она вообще есть, а усредняет `pick` только при ничьей по частоте — сегодня это ирис Моники и больше ничего

Угадывать он отказывается: сайт на любой отсутствующий путь отвечает `200` с HTML-страницей, поэтому скрипт смотрит на `content-type`, а не на код ответа, и падает, если в читаемом CSS-правиле пропал цвет. Раз в неделю его гоняет отдельный workflow: и только если сайт разошёлся, тот коммитит перезамеренную палитру и перегенерированный `dist/` в ветку и открывает pull request «canonize: ddlc.moe drifted», в теле которого — таблица всех сдвинувшихся цветов, того, куда они сдвинулись, и каким методом получены. Метод — половина новости: цвет, съехавший с `mode` на `mean`, говорит, что сайт перестал заливать эту область плоско, а по одному хексу этого не видно. Цвет не меняется без того, чтобы кто-то посмотрел на диф

## Поменять цвет

Правишь руками `palette.json` для того, чего на сайте нет, затем:

```sh
./generate.sh          # нужен jq
```

Коммитишь оба. CI пересобирает `dist/` и сравнивает с закоммиченным, так что разъехаться они не могут
